# VocaRabbit 实施计划

日期：2026-05-08

## 1. 目标

这份计划用于把当前已经形成的设计文档，转成可执行的实现顺序。

当前已完成的设计文档：

- 页面架构设计
- 统计页设计
- 选词页设计
- 复习页设计
- 设置页设计
- 单词详情抽屉设计

目标不是一次做完所有页面，而是按依赖关系推进，保证每个阶段完成后产品都是可运行、可验证的。

## 2. 当前代码基础

当前已存在：

- 基础首页原型
- 学习页
- 完成页
- 词表 JSON 构建脚本
- IndexedDB 基础存储
- 底部四按钮导航雏形

当前尚缺：

- 真正的复习页定型
- 选词页
- 统计页
- 设置页
- 单词详情抽屉
- 选词状态模型
- 答题事件日志模型

## 3. 关键依赖

### 3.1 先做的数据层

必须先补：

1. WordSelectionState
2. ParentSetting 扩展字段

建议后做：

1. AnswerEvent

原因：

- 没有 WordSelectionState，选词页和详情抽屉的启用/暂停操作无法稳定落地。
- 没有 ParentSetting 扩展，设置页只能做半套。
- AnswerEvent 不影响第一阶段页面上线，但影响统计页的高级分析能力。

## 4. 推荐开发顺序

### Phase 0：基础模型与路由整理

目标：给后续页面开发打底。

任务：

1. 扩展路由定义：复习 / 选词 / 统计 / 设置 / 学习 / 完成
2. 新增 WordSelectionState 模型与存储
3. 扩展 ParentSetting 模型与存储
4. 把首页当前 HomePage 明确为 ReviewPage 方向

验收标准：

- 路由结构清晰
- 新模型可以持久化
- 现有页面不被破坏

### Phase 1：复习页定型

目标：把默认首页稳定成真正的复习页。

任务：

1. 调整英雄区和任务摘要
2. 固定四词预览区来源
3. 保留底部导航
4. 补轻量学习建议区

验收标准：

- 打开应用后直接知道今天该做什么
- 可以一键进入学习页
- 页面不承担选词和统计的复杂职责

### Phase 2：设置页

目标：先把任务量和基础开关做出来。

任务：

1. 每日新词数控制
2. 每日复习上限控制
3. 发音/图片/例句/提示开关
4. 数据导出导入占位
5. 重置学习数据确认流

验收标准：

- 调整参数后能影响复习页和后续压力估算
- 设置变更立即持久化

### Phase 3：单词详情抽屉

目标：建立跨页面通用层。

任务：

1. 在复习页词卡上打开抽屉
2. 展示基础词信息、图片、牛津树定位、学习状态
3. 接入发音按钮
4. 接入启用/暂停状态入口的占位

验收标准：

- 在不离开当前页的前提下能看词详情
- 抽屉可在多个页面复用

### Phase 4：选词页 MVP

目标：打通家长配置学习范围的核心能力。

任务：

1. 三栏式布局
2. 左侧筛选栏
3. 搜索
4. 中间词卡区
5. 启用/暂停操作
6. 右侧词篮摘要
7. 和复习页的联动

验收标准：

- 家长可以筛选并启用词
- 可以看到当前词量和未来基础压力
- 应用方案后会影响复习页任务生成

### Phase 5：统计页 MVP

目标：给家长提供有效反馈，而不是装饰性图表。

任务：

1. 顶部概览卡
2. 热力图
3. 掌握结构
4. 高频错误词
5. 未来复习压力预测
6. 与选词页、复习页的基础跳转联动

验收标准：

- 家长能判断今天是否完成
- 能看到最薄弱词和未来压力

### Phase 6：增强统计与增强选词

目标：在 MVP 跑通后补决策质量。

任务：

1. 错误主题模块
2. 压力建议动作
3. 列表视图和批量操作
4. 自定义词单

### Phase 7：答题事件日志与高级统计

目标：补足统计页第二层分析能力。

任务：

1. 新增 AnswerEvent
2. 记录每次答题事件
3. 接入按题型趋势
4. 接入更细的错误轨迹

## 6. 每阶段验证策略

### 6.1 页面阶段

每做完一个页面，都至少做：

1. TypeScript 构建通过
2. 页面在浏览器里可打开
3. 关键交互至少人工点一遍

### 6.2 数据阶段

新增模型时至少验证：

1. IndexedDB 可写入
2. 刷新后数据仍在
3. 页面状态能正确恢复

### 6.3 联动阶段

跨页能力至少验证：

1. 选词变化影响复习页
2. 设置变化影响复习和统计
3. 统计页可跳到选词页或复习页

## 7. 风险点

### 7.1 过早做复杂统计

风险：没有 AnswerEvent 还试图做题型趋势，结果会失真。

应对：

- 先只做当前模型真正支持的统计。

### 7.2 选词状态和学习记录混在一起

风险：数据语义混乱，后续难以维护。

应对：

- 单独建立 WordSelectionState。

### 7.3 首页继续堆功能

风险：复习页变得像后台，孩子入口变重。

应对：

- 把复杂管理能力都留给选词页、统计页、设置页。

## 8. 建议提交节奏

建议不要一次做成一个超大提交，而是按阶段切：

1. `Add selection and settings models`
2. `Refine review page`
3. `Add settings page`
4. `Add word detail drawer`
5. `Add word selection page`
6. `Add statistics page MVP`

## 9. 结论

当前最稳妥的开发顺序是：

1. 先补模型
2. 再稳住复习页和设置页
3. 然后做详情抽屉
4. 再做选词页
5. 最后做统计页 MVP

这样做的好处是：

- 每一步都能看到成品
- 每一步都有真实验证方式
- 不会把统计页做在不存在的数据基础上
- 不会让首页承担过多职责
